# Component libraries fill Pencraft's missing anatomy

Pencraft already teaches its assistant how to choose a direction, build a hierarchy and avoid generated-looking design, but it teaches almost nothing about what a standard control is: the only control dimensions in the whole guide are button label room of 8 to 12, chip room of 4, 8 of clearance and "about 44 high" on a phone (`app/src/craft.rs:89-91`), and the only ready-made component anatomy in the product lives inside the iOS-style `liquid-glass` skill. The thirteen libraries studied here supply exactly that missing layer, and they agree far more than they differ: a 4 px grid, a control-height ladder of 24/28/32/36/40, 14 px medium-weight labels, 16 px icons, 1 px hairlines drawn as translucent rings, tiny layered shadows, a derived radius scale with concentric nesting, and a fixed list of states per control. The highest-value change is not more taste guidance but a neutral **`ui-components` skill** with tokens, per-component measurements and a state board, plus a short "standard controls" block in `CRAFT`. Just as important, four of Pencraft's current mechanisms actively work against a user who asks for standard components: the dealt directions force a ground and a lead face on every first message, the counted review flags Inter-only type and "outline plus shadow", the radius limit of four is below what a faithful shadcn screen uses, and the second-model critic requires an originality score of 7 to pass. Three engine gaps block faithful reproduction of library recipes: no shadow spread (so no ring recipes and no Tailwind `md`/`lg` shadows), no tabular numerals, and no variants or states. Several widely copied values changed in 2026 (shadcn/ui's default is now Base UI with the 32 px "Nova" style, destructive buttons are tints, overlays use a 10% scrim), so the report marks which numbers are current, which are legacy and which are unverified.

## Pencraft teaches direction and tidiness, but four of its own rules punish standard components

The current state is easiest to understand as three layers with one hole. The guide returned by `get_guide` concatenates the format guide (`app/src/agent.rs:21-114`), a one-line skills index, the design method `CRAFT` (`app/src/craft.rs:20-169`) and the installed fonts. `CRAFT` is strong on method: classify the surface, set variables first, build hierarchy, avoid a list of generated-design tells, then judge a screenshot as someone else's work. The counted review on every screenshot runs about 35 geometric and colour checks (`app/src/review.rs`), and a second model scores large in-app runs on quality, originality, craft and function (`app/src/chat/critic.rs:31-52`). What none of these layers contains is component knowledge. A text search of the guide found no mention of input, select, checkbox, radio, switch, dialog, menu, tooltip, toast, drawer, command palette, tabs as a control, accordion, skeleton, avatar, breadcrumb or pagination. `CRAFT` tells the model that working screens must use the standard navigation and controls people already know (`craft.rs:35-38`) and then never says what those look like. Token guidance stops at six colour roles, a 4-step spacing scale, "one radius for controls, one for cards" and a one-line shadow rule.

The more urgent finding is that four existing mechanisms push the assistant away from what a user who asks for "standard components" wants. First, every first message of an in-app conversation carries dealt directions: three of 24 worlds, one of five grounds and one of six lead-face kinds, with the ground and face declared not the model's to choose (`craft.rs:173-238`). A request such as "make me a settings dialog with standard components" is still dealt a forced face and ground. Second, the counted review flags a design whose only family is on the default list, which includes Inter (`review.rs:917-921`), while shadcn/ui's default configuration is Inter on a neutral base ([config.ts](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/config.ts)); a faithful answer is reported as a fault. Third, the review flags outline and shadow together on two or more frames (`review.rs:324-326, 1079`) and `CRAFT` says to set a surface apart in one way only, yet shadcn/ui, Radix Themes and Beautiful UI all draw every floating surface as a 1 px translucent ring plus a soft shadow ([vega.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-vega.css); [shadow.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/styles/tokens/shadow.css); [Beautiful UI CSS](https://beautifului.dev/_next/static/css/916c3f25c8795666.css)). Fourth, the critic passes a design only when originality reaches 7 and weighs it double; for a component sheet in a named library's style, originality is the wrong axis and fidelity is the right one.

Smaller frictions follow the same pattern. The review allows four distinct radii, but shadcn's classic style legitimately uses 4 (checkbox), 6 (menu item), 8 (control), 10 (tab list) and 14 (card) on one screen. The review requires 6:1 contrast under 13 px (`review.rs:22-31`); shadcn's 12 px muted labels use `muted-foreground`, approximately `#737373` on white, which is about 4.7:1 (my calculation from the approximate hex conversion, not a sourced figure), so a faithful copy fails Pencraft's stricter bar. Common focus-ring recipes cannot be drawn without tripping the glow check (a vivid, zero-offset, blurred shadow, `review.rs:257-264`) or the block-shadow check (offset with no blur, `review.rs:265-267`), and cannot be drawn as a true ring at all because shadow `spread` is not read (`app/MECHANICS.md:59`). The starter document contradicts the guide: it ships Inter everywhere, an indigo `#4f46e5` accent, three equal cards with outline plus shadow and an indigo-to-cyan gradient (`app/src/samples.rs:4-153`), so "match what is there" leads straight into notes the review then raises. Finally, the in-app chat brief does not include the skills index (`app/src/chat.rs:59-63`), so on the Claude Code route a model that does not call `get_guide` never learns a skill exists.

## Each library contributes a different layer of the missing knowledge

### shadcn/ui supplies the token set, the per-component numbers and the 2026 style axis

shadcn/ui is the most complete single source because every number can be read from its style files. The token shape is a set of surface and foreground pairs (background, card, popover, primary, secondary, muted, accent, destructive) plus border, input, ring, chart and sidebar tokens, defined in OKLCH ([themes.ts](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/themes.ts)). The semantics matter more than the values: `muted` is for subtle surfaces and secondary text, `accent` is the hover and highlight surface, `border` is for layout lines and `input` for form-control borders, `ring` for focus ([theming.mdx](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/(root)/theming.mdx)). In the neutral theme only `destructive` has chroma; secondary, muted and accent are one grey, which is the numeric form of the library's restraint. Dark mode is not an inversion: surfaces step up in lightness (background 0.145, card and popover 0.205, muted 0.269) and borders become **white at 10%**, input borders **white at 15%** ([themes.ts](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/themes.ts)). The hex values in the table below are the note-taker's approximate sRGB conversions, which match Tailwind's neutral ramp; the source is OKLCH only, so treat the hex as unverified to the last digit.

| Role | Light (approx. hex) | Dark (approx. hex) |
|---|---|---|
| background / foreground | `#ffffff` / `#0a0a0a` | `#0a0a0a` / `#fafafa` |
| card, popover | `#ffffff` | `#171717` |
| primary / on-primary | `#171717` / `#fafafa` | `#e5e5e5` / `#171717` |
| secondary = muted = accent | `#f5f5f5` | `#262626` |
| muted-foreground | `#737373` | `#a1a1a1` |
| border / input | `#e5e5e5` / `#e5e5e5` | `#ffffff1a` / `#ffffff26` |
| ring | `#a1a1a1` | `#737373` |
| destructive | about `#e7000b` | about `#ff6467` |

The radius scale is derived from one base value by multiplication: 0.6, 0.8, 1, 1.4, 1.8, 2.2 and 2.6 times `--radius`, which at the default 10 px gives **6, 8, 10, 14, 18, 22 and 26** ([theming.mdx](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/(root)/theming.mdx)). Typography is deliberately narrow: 14/20 medium for nearly everything interactive, 12 px for menu group labels, shortcuts, badges, tooltips and keycaps, 16/24 medium for card titles, and muted-foreground for all secondary text; weights are 400 and 500, with 600 reserved for KPI figures ([vega.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-vega.css)). Hierarchy comes from weight and colour rather than size. Icons default to 16 px beside 14 px text, 12 px in extra-small buttons and badges, and Lucide is the default set, which is also Pencraft's only bundled set ([vega.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-vega.css)).

The per-component measurements below are from the "Vega" style, described by the project as the classic look, with "Nova" (the 2026 default) in brackets where it differs ([vega.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-vega.css); [style-nova.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-nova.css)). Pixel values assume Tailwind's standard 4 px unit, a conversion the notes did not re-fetch.

Elevation is minimal and assigned by role: `shadow-xs` on controls, `shadow-sm` on the active tab and slider thumb, `shadow-md` on popovers and menus, `shadow-lg` on sub-menus, sheets and toasts, and no shadow at all on dialogs in Vega and Nova because the scrim separates them ([vega.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-vega.css)). States are communicated with border colour and a ring, never a glow: focus recolours the 1 px border to `ring` and adds a **3 px ring at 50%** with no offset; invalid uses a destructive border and a 3 px ring at 20% (40% in dark); disabled is 50% opacity. The 2026 destructive button is a tint (destructive at 10% with destructive text), not solid red, and outline and ghost hover use `muted`.

Page-level blocks repeat a small rhythm of 8, 16 and 24: a dashboard has a 48 px header, a 288 px inset sidebar, KPI cards on a 16 px gap with a 24 px semibold tabular figure; an auth page centres a 384 px card with 24 px page padding ([dashboard-01](https://github.com/shadcn-ui/ui/tree/main/apps/v4/registry/bases/base/blocks/dashboard-01); [login-01](https://github.com/shadcn-ui/ui/tree/main/apps/v4/registry/bases/base/blocks/login-01)). The project's own agent skill reduces composition to two formulas (a settings page is tabs plus cards plus form controls; a dashboard is sidebar plus cards plus chart plus table) and a set of always-on rules that transfer directly to Pencraft: semantic colours rather than raw values, built-in variants before tokens before new variables, full card composition rather than one content box, a dedicated empty-state component, and a title on every dialog ([SKILL.md](https://github.com/shadcn-ui/ui/blob/main/skills/shadcn/SKILL.md); [rules/styling.md](https://github.com/shadcn-ui/ui/blob/main/skills/shadcn/rules/styling.md)).

The architectural lesson is the style axis. shadcn/ui now models a look as three orthogonal choices: a colour theme (variables), a style (geometry, spacing and type per slot) and icon and font choices. Eight styles map the same component slots to different numbers: Vega 36 px controls with 8 px radius, Nova 32 with 10, Maia and Luma 36 with pills, Lyra 32 square with 12 px mono text, Mira 28 with 12 px text, Sera 40 with underline inputs and uppercase labels, Rhea 32 with 18 px radius ([registry/styles](https://github.com/shadcn-ui/ui/tree/main/apps/v4/registry/styles)). The project explains that it added styles rather than a spacing multiplier because changing the multiplier would change what familiar utilities mean ([Rhea changelog](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/changelog/2026-05-rhea.mdx)). A "preset" of base colour, accent, style, radius, font and icon library is the minimal state an assistant needs to draw consistently, and Pencraft's theme axes can hold it.

### Base UI and Radix supply the state list, the part names, the placement rules and a colour logic

Base UI (v1.9.0, October 2026, 37 components) and Radix Primitives (30 components) contribute the answer to "which states and parts must be drawn". Base UI exposes a complete form-control state set on every control and on every part of a field: disabled, read-only, required, valid, invalid, dirty, touched, filled and focused, plus checked, unchecked and indeterminate on checkable controls and placeholder on selects ([Base UI Field](https://base-ui.com/react/components/field); [Base UI Switch](https://base-ui.com/react/components/switch)). List items carry highlighted (the keyboard or hover cursor) and selected as independent states that can co-occur, so a correct menu mock-up shows one highlighted row and, separately, a check on the selected row ([Base UI Select](https://base-ui.com/react/components/select)). A practical minimum per interactive control, derived from these lists, is default, hover, pressed, focus-visible and disabled, plus the control's own states: checked and indeterminate, open, highlighted versus selected, placeholder versus filled, invalid, read-only and loading. Base UI validates on submit by default, so the invalid state belongs on a "after submit" frame, not on a pristine form ([Base UI Field](https://base-ui.com/react/components/field)).

Base UI's part names are the better layer-naming convention for a canvas because they are uniform across every popup: Trigger, Backdrop, Positioner, Popup, Arrow, Title, Description, Close; Track, Indicator, Thumb; Item, ItemText, ItemIndicator; Group, GroupLabel; Separator ([Base UI Dialog](https://base-ui.com/react/components/dialog); [Base UI Slider](https://base-ui.com/react/components/slider)). The Combobox adds an explicit Empty part, which makes "no results" a first-class state to draw, and the field anatomy order is Label, Control, Description, Error ([Base UI Combobox](https://base-ui.com/react/components/combobox); [Base UI Field](https://base-ui.com/react/components/field)). Usage guidance has visual consequences: prefer a combobox to a select when the list needs filtering, never make a context menu the only route to an action, and treat tooltips as supplementary labels only ([Base UI Combobox](https://base-ui.com/react/components/combobox); [Base UI Context Menu](https://base-ui.com/react/components/context-menu); [Base UI Tooltip](https://base-ui.com/react/components/tooltip)).

Placement rules come from the styled Radix Themes layer rather than the unstyled defaults (which are zero offsets): tooltips, selects and dropdown menus sit **4 px** from their trigger, popovers and hover cards **8 px**, aligned to the trigger's start edge, kept **10 px** from the viewport edge, and never narrower than the trigger; sub-menus are shifted up by the popup's inner padding so the first sub-item lines up with its parent ([radix-ui/themes components](https://github.com/radix-ui/themes/tree/main/packages/radix-ui-themes/src/components); [popover.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/popover.css)). Arrows are 10 x 5 in Radix and 12 x 6 in Base UI's demo ([Radix Popover](https://www.radix-ui.com/primitives/docs/components/popover); [Base UI Popover demo CSS](https://base-ui.com/react/components/popover)). Nested Base UI dialogs get no second backdrop; the demo shifts the parent 20 px and scales it down 10% per level ([Base UI Dialog](https://base-ui.com/react/components/dialog)).

Radix Themes is the strictest token system in the set. Space is 4, 8, 12, 16, 24, 32, 40, 48, 64; type is 12/16, 14/20, 16/24, 18/26, 20/28, 24/30, 28/36, 35/40 and 60/60 with letter-spacing that tightens from +0.0025em at 12 px to -0.025em at 60 px; radius is 3, 4, 6, 8, 12, 16 multiplied by a theme factor ([space.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/styles/tokens/space.css); [typography.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/styles/tokens/typography.css); [radius.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/styles/tokens/radius.css)). Controls come in heights **24, 32, 40 and 48** with padding-x 8, 12, 16, 24 and font 12, 14, 16, 18; text fields and select triggers stop at 40; checkboxes are 14, 16, 20; switch tracks are 1.75 times their height; panel padding and radius scale together (12/8, 16/8, 24/12, 32/12) ([base-button.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/_internal/base-button.css); [text-field.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/text-field.css); [switch.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/switch.css); [card.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/card.css)). Even when the radius setting is "full", panels never become pills and a checkbox never becomes round, to avoid confusion with a radio ([Radix Themes Radius](https://www.radix-ui.com/themes/docs/theme/radius)).

Radix Colors gives every step of a 12-step scale a job: 1 and 2 are backgrounds, 3, 4 and 5 are component fills at rest, hover and pressed or selected, 6 is a subtle border, 7 an interactive border, 8 a stronger border or focus ring, 9 the solid, 10 its hover, 11 low-contrast text and 12 high-contrast text ([Understanding the scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)). Steps 11 and 12 are guaranteed APCA Lc 60 and Lc 90 on a step-2 background of the same scale, and five solids (sky, mint, lime, yellow, amber) need dark text ([Understanding the scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)). Greys are paired to the accent (mauve for reds and purples, slate for blues, sage for greens, olive for lime, sand for yellows and browns), which is the precise version of Pencraft's "greys tinted toward the dominant colour" ([get-matching-gray-color.ts](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/helpers/get-matching-gray-color.ts)). Every variant is then a fixed recipe over that scale ([base-button.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/_internal/base-button.css)):

| Variant | Rest | Hover | Pressed | Disabled |
|---|---|---|---|---|
| solid | fill 9, contrast text | fill 10 | 10, slightly darker | fill gray-a3, text gray-a8 |
| soft | fill a3, text a11 | a4 | a5 | fill gray-a3, text gray-a8 |
| outline | 1 px inset ring a8, text a11 | fill a2 | fill a3 | ring gray-a7, text gray-a8 |
| ghost | text a11 only | fill a3 | fill a4 | text gray-a8 |

Two rules generalise from this table. Rest, hover and pressed are consistently **one step apart**, and in dark mode step 10 is lighter than step 9 while in light mode it is darker, so "hover equals darker" must never be hard-coded ([light.ts](https://github.com/radix-ui/colors/blob/main/src/light.ts); [dark.ts](https://github.com/radix-ui/colors/blob/main/src/dark.ts)). Disabled is drawn by colour rather than opacity, one recipe for every control, which keeps disabled controls legible on any ground. Radix Themes also shows a conforming focus ring: a **2 px solid outline** in the focus colour, offset +2 on solid buttons, checkboxes, radios and switches and -1 on fields and soft buttons ([base-button.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/components/_internal/base-button.css)). Base UI states plainly that indicating focus is the developer's job and recommends APCA for contrast ([Base UI Accessibility](https://base-ui.com/react/overview/accessibility)). Its own docs demos are a useful fallback "wireframe" theme: about seven greys, 32 px controls, 14 px text, zero radius and a 2 px outline, covering every state with the fewest tokens ([Base UI Button demo CSS](https://base-ui.com/react/components/button)).

### Sonner, Vaul, cmdk and NumberFlow each define one component completely

Sonner gives a full toast specification. The card is **356 px wide**, padded 16, radius 8, with a 1 px border at hsl(0 0% 93%) and a single shadow of y 4, blur 12, black 10%; text is 13 px with a 500 title at line-height 1.5 and a 400 description at 1.4, 2 px apart; the icon slot is 16 px; the action button is a 24 px-high inverted pill with 8 px padding, 4 px radius and 12/500 text ([Sonner styles.css](https://github.com/emilkowalski/sonner/blob/main/src/styles.css); [Sonner index.tsx](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx)). At most three toasts are visible; each one behind the front is offset by 14 px and scaled down 5%, takes the front toast's height and hides its content, so it reads as an empty card edge. The default position is bottom-right, 24 px from the edges (16 on mobile, where the toast spans the width minus 16 each side). Without the rich-colours option, success and error are the neutral card with only an icon; with it, they are tinted cards (pale fill, slightly stronger border, saturated text), never solid colour blocks. For a static tool the transferable ideas are the peeking-edge stack to show "more behind", the expanded state as a plain column with 14 px gaps, and entering and leaving along one axis.

Vaul ships almost no visuals, which is itself the lesson: a bottom sheet is a handle plus behaviour. The handle is **32 x 5 px**, fully round, `#e2e2e4` at 70% opacity, with an invisible hit area of at least 44 x 44 ([Vaul style.css](https://github.com/emilkowalski/vaul/blob/main/src/style.css)). The optional background effect scales the page to (viewport width - 26) / viewport width, rounds it to 8 px and moves it 14 px down on a black body; a nested sheet scales its parent to (width - 16) / width and lifts it 16 px ([use-scale-background.ts](https://github.com/emilkowalski/vaul/blob/main/src/use-scale-background.ts); [constants.ts](https://github.com/emilkowalski/vaul/blob/main/src/constants.ts)). The docs example uses a 40% black overlay ([Vaul docs](https://vaul.emilkowal.ski/getting-started)). Snap points are best drawn as separate frames (peek, half, full) with the overlay present only at the top one. Sheet corner radius, background and handle margins are user styling; the commonly copied values (10 px top radius, 48 x 6 handle) were recalled from memory by the note-taker and are **unverified**.

cmdk's four demo skins fix the command-palette skeleton: a **640 px** card with a shadow of y 16, blur 70, black 20%, radius 8 to 16; an input row with 15 to 18 px text and a grey placeholder; a hairline; a list 300 to 400 px tall; 12 px grey group headings inset 8; rows 40 to 48 high with 14 px labels and 16 to 18 px icons, 4 px apart; right-aligned 20 px keycaps with 4 px radius and 12 px text; and exactly one selected row ([cmdk themes](https://github.com/pacocoursey/cmdk/tree/main/website/styles/cmdk); [globals.scss](https://github.com/pacocoursey/cmdk/blob/main/website/styles/globals.scss)). The skins differ in selection idiom: a subtle alpha fill (Vercel), a fill plus a 3 px accent bar (Linear), a neutral fill with a 40 px footer of action hints (Raycast) and a saturated accent fill (Framer). Because cmdk filters and re-sorts by a fuzzy score that favours continuous and word-start matches ([command-score.ts](https://github.com/pacocoursey/cmdk/blob/main/cmdk/src/command-score.ts)), a realistic "typed query" frame shows fewer, re-ordered rows, drops empty groups with their headings, hides separators, keeps the first row selected, and has an empty state of one centred 14 px grey line 48 to 64 px tall. These skins are a third party's recreations of the named products, not the products themselves.

NumberFlow's lesson for a static tool is about figures, not motion. It formats through `Intl.NumberFormat`, treats prefix, suffix and currency as separately styleable parts, and its docs recommend tabular numerals so digits keep equal width ([NumberFlow docs](https://number-flow.barvian.me/)). shadcn/ui applies tabular numerals to numeric values by default and Magic UI's number ticker does the same ([vega.css](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles/style-vega.css); [number-ticker.json](https://magicui.design/r/number-ticker.json)). The static rules that follow are: any number that can change or sits in a column uses tabular figures; numeric columns are right-aligned with fixed decimals; thousands are grouped; compact notation suits dense tiles and full precision suits detail views; trends carry a sign; and unit or currency parts can be lighter or smaller.

### The emilkowalski/skills repository shows how to write the skills and which motion rules survive in a still picture

The repository holds 18 Agent Skills, nearly all about motion and polish, and its value to Pencraft is twofold. First, `pick-ui-library` is a short lookup table that names Base UI for unstyled primitives, cmdk for command menus, Sonner for toasts, Vaul for drawers and NumberFlow for animated numbers; shadcn/ui and Radix are not mentioned in it at all ([pick-ui-library](https://github.com/emilkowalski/skills/blob/main/skills/pick-ui-library/SKILL.md)). Its procedure is the part worth copying: identify the task rather than the library the user named, prefer what is already installed, recommend exactly one option rather than a menu, and say so explicitly when leaving the curated list. Second, the authoring pattern is consistent across skills: a narrow single purpose with hand-offs to siblings in the description, a persona with two named failure modes, numbered hard rules, an ordered gate, every value in a table with a ban on approximated values, a "never / instead" table, per-phase completion criteria, a mandatory output format, and heavy catalogues split into sibling files loaded on an explicit cue ([animate](https://github.com/emilkowalski/skills/blob/main/skills/animate/SKILL.md); [break-ui](https://github.com/emilkowalski/skills/blob/main/skills/break-ui/SKILL.md)). The author's stated method is to write down why each choice feels right and hand those reasons to the agent as strict rules with tables and numbers ([Agents with Taste](https://emilkowal.ski/ui/agents-with-taste)). One caution: the repository repeats its canonical tables in several skills, and a November 2026 commit had to fix contradictions between them ([commit history](https://github.com/emilkowalski/skills/commits/main)); Pencraft should keep one tokens file and reference it.

Several rules survive without animation. Popovers are visibly attached to and aligned with their trigger; a pressed-state frame is the control at 97% scale; elements enter from the edge they live on; hit areas are at least 44 px even when the visible element is 5 px tall; large headings take about -0.02em tracking and body text a 65-character measure; changing numbers use tabular figures; counts are pluralised properly; timestamps switch to absolute dates after a week ([ui-cheatsheet.md](https://github.com/emilkowalski/skills/blob/main/ui-cheatsheet.md); [gestures](https://github.com/emilkowalski/skills/blob/main/skills/gestures/SKILL.md)). Three skills map onto features Pencraft lacks. `break-ui` stresses a design with plausible worst-case data (a long hyphenated surname, a 64-character email, 1,284 members) across states Demo, Worst case, Empty, One and 1,000 rows, and forbids truncating numbers or dates ([break-ui](https://github.com/emilkowalski/skills/blob/main/skills/break-ui/SKILL.md)). `prototype` builds three variants, each on a named axis and named by direction rather than "Option A" ([prototype](https://github.com/emilkowalski/skills/blob/main/skills/prototype/SKILL.md)). `learn-taste` turns a session's corrections into rules with a reason and a dated quote in a DESIGN.md ([learn-taste](https://github.com/emilkowalski/skills/blob/main/skills/learn-taste/SKILL.md)).

### Beautiful UI and RareUI supply the finish: layered elevation, rings, highlights and nesting

Beautiful UI is a small MIT showcase of 21 agent-interface primitives with no registry or agent surface, and its worth is a disciplined token system. It names four radii (**chip 6, control 8, card 10, window 14**), nine neutral surface, ink and line steps with a very small blue chroma so that grey is never pure grey, and six elevations each built as a 1 px ring plus a multi-layer shadow whose individual alphas never exceed 5% ([Beautiful UI CSS](https://beautifului.dev/_next/static/css/916c3f25c8795666.css)). The overlay stack, for example, is five layers that halve each time: y 25 blur 50 at 5%, 12/24 at 4%, 6/12 at 3%, 3/6 at 2% and 1.5/3 at 2%. This matters for Pencraft specifically because these stacks use **zero spread** (one layer of one stack excepted), so they are expressible today with Pencraft's stacked shadows, whereas Tailwind's `md` and `lg` shadows rely on negative spread. In dark mode the drop shadow shrinks to one or two layers and the ring carries the edge, with ring alpha rising with elevation: white at 10% for buttons, 11% for cards, 13% for raised and 15% for overlays. Filled buttons get a 1 px inset top highlight of white at 14%; unchecked controls use a 1.5 px inset ring; overlapping avatars are cut apart with a 1.5 px ring in the background colour; the focus ring is 1.5 px of accent ([beautifului.dev](https://beautifului.dev)). Its markup shows a dense scale: 13, 12.5, 12 and 11.5 px text, medium weight four times as often as semibold, a default control height of 32 with 28 px icon buttons, 14 and 12 px icons, and three inks for hierarchy. Its component list (thinking trace, tool chips, approval card, prompt bar, task rows, diff table, recommendation card, context cards) is a ready inventory for agent-product screens.

RareUI is a one-person library with about 22 documented components against marketing claims of 50+ and 100+, and one of its own shadow values is malformed CSS, so it is a recipe book rather than an authority ([registry index](https://rareui.in/r/index.json); [GlassShimmerButton.tsx](https://github.com/Codewithswappy/RareUI/blob/main/components/rareui/GlassShimmerButton/GlassShimmerButton.tsx)). Four static recipes are worth keeping as opt-in presets: a glass pill (dark translucent fill, 1 px white-10% border, a top hairline gradient through white 40% and a fainter bottom one); neumorphism as four shadow layers, two outer and two inset, mirrored ([SoftButton.tsx](https://github.com/Codewithswappy/RareUI/blob/main/components/rareui/SoftButton/SoftButton.tsx)); a premium card built from a thick frame, a 20 px grid at white 10%, a noise overlay and a radial spot, with radii stepping 27, 26, 24 across layers ([PremiumProfileCard.tsx](https://github.com/Codewithswappy/RareUI/blob/main/components/rareui/PremiumProfileCard/PremiumProfileCard.tsx)); and a coloured under-glow as a shadow with large y offset and negative spread in the button's own colour at 20% ([PremiumButton.tsx](https://github.com/Codewithswappy/RareUI/blob/main/components/rareui/PremiumButton/PremiumButton.tsx)).

### Magic UI and Aceternity UI reduce to five drawable ingredients and a budget

Nearly every effect in these two libraries reduces to ingredients a static tool can draw. The first is a hairline pattern faded by a vignette: a 40 px grid of 1 px lines (`#262626` or `#171717` on black, `#e4e4e7` on white) or 16 to 20 px dots, under an overlay of the page colour that is transparent in the centre and solid at the edges ([grid-background-demo.json](https://ui.aceternity.com/registry/grid-background-demo.json); [grid-pattern.json](https://magicui.design/r/grid-pattern.json)). The second is a blurred light: Aceternity's spotlight is one white ellipse at 21% opacity under a very large blur, and its lamp is two cyan conic wedges 480 x 224 meeting at top centre over blurred ellipses with a crisp 480 x 2 line as the tube ([spotlight.json](https://ui.aceternity.com/registry/spotlight.json); [lamp.json](https://ui.aceternity.com/registry/lamp.json)). The third is a gradient ring: a 1 to 2 px stroke filled with a linear, radial or conic gradient, optionally duplicated behind with a large blur at 60 to 80% for a halo ([border-beam.json](https://magicui.design/r/border-beam.json); [background-gradient.json](https://ui.aceternity.com/registry/background-gradient.json)). The fourth is a streak: a 1 or 2 px line running transparent, colour, transparent, doubled with a 4 px blurred copy ([sparkles-demo.json](https://ui.aceternity.com/registry/sparkles-demo.json)). The fifth is a dark card with a white 10 to 20% border and an inset glow; Magic UI's bento card in light mode uses a three-layer shadow of a 1 px 3% ring, y 2 blur 4 at 5% and y 12 blur 24 at 5% ([bento-grid.json](https://magicui.design/r/bento-grid.json)). Pencraft can express all five with gradient fills and strokes, angular gradients, layer blur and stacked shadows; masks and blend modes are missing, so vignettes must be drawn as gradient overlays in the page colour.

The page skeleton the libraries promote is a centred hero with a 36 to 72 px bold heading clipped to a silver vertical gradient (neutral-50 to neutral-400), a 16 to 18 px muted paragraph capped near 512 to 576 px, two buttons, and a framed screenshot 80 px below in a double border (outer radius 24 with 16 padding, inner radius 12), inside a 1280 px container ([spotlight-demo.json](https://ui.aceternity.com/registry/spotlight-demo.json); [hero-section-demo-1.json](https://ui.aceternity.com/registry/hero-section-demo-1.json)). Bento grids are 3 columns with 288 or 352 px rows and a 16 px gap, with deliberately unequal spans ([bento-grid.json](https://ui.aceternity.com/registry/bento-grid.json); [bento-demo.tsx](https://raw.githubusercontent.com/magicuidesign/magicui/main/apps/www/registry/example/bento-demo.tsx)). Magic UI's device mockups (Safari 1203 x 753, iPhone 433 x 882) use two greys only, with no coloured traffic lights, which is why they sit in any palette ([safari.json](https://magicui.design/r/safari.json); [iphone.json](https://magicui.design/r/iphone.json)). Exact layouts for pricing, FAQ, CTA and footer sections are paywalled in both libraries and were not obtained.

The critique matters as much as the recipes, and here the libraries and Pencraft's existing guide are in tension by design. Pencraft's anti-pattern list and review already treat gradient text, glows, blurred blobs and equal cards as tells unless the user's words earn them, and the evidence supports keeping that default. Critics target the look these libraries make cheap: dark ground with a purple-blue glow, animated gradient borders, gradient headline text and equal-weight bento tiles ([AI Smells: Gradient Fog](https://aismells.pages.dev/gradient-fog.html); [AI Smells: Bento Box Sprawl](https://aismells.pages.dev/bento-box-sprawl.html); [jeangalea.com](https://jeangalea.com/ai-ui-looks-generic/)). These are blogs and community checklists, not authoritative studies, and no named-designer critique of either library was found. The useful synthesis is a budget for when such effects are requested: at most one atmospheric background per page, at most one gradient ring or halo per viewport, gradient text only on the hero heading, an accent chosen from the brand rather than the libraries' default orange-to-violet or cyan-to-violet, and bento only with a dominant tile and real content. A frozen frame removes the motion that justified meteors, shimmer and marquees, so a static tool should lean further toward restraint than the live libraries do. On licensing, Magic UI is MIT, while Aceternity's licence forbids redistributing its items as a kit; teaching general recipes is different from bundling a recreated Aceternity kit, and this is not legal advice ([Aceternity licence](https://ui.aceternity.com/licence)).

### 21st.dev shows how an assistant should select, adapt and stay on brief

21st.dev's code is gated (two free copies a day), so it contributed no verifiable measurements; its contribution is process. Its catalogue counts show where demand sits: buttons 2,043, cards 1,780, forms 1,522, heroes 1,152 and inputs 949, against sidebars 95, empty states 77 and onboarding 53 ([popular page](https://21st.dev/community/components/popular)). About a quarter of its top 60 are plain, well-finished form primitives from Origin UI, and its most-used themes are restrained neutrals and brand clones such as Vercel, Modern Minimal and Claude ([popular page](https://21st.dev/community/components/popular); [themes page](https://21st.dev/community/themes)). The stale category counts in its markdown pages and an outside review's pricing claims both conflict with the live site and should be ignored.

Its published agent skills are the most developed answer in this research to "exactly what the user requested". The build skill ranks explicit project facts above generic taste, tells the agent to search before generating and reuse installed primitives first, to prefer project tokens over new arbitrary values and existing components over lookalikes, to preserve established density, radii, typography and iconography unless a redesign is requested, to avoid decorative gradients, glass, huge headlines and animation unless the project supports them or the user asks, and never to claim a component or token exists without inspecting it ([build skill](https://21st.dev/.well-known/skills/21st-ui-build/SKILL.md)). Search and generation are reranked against a per-project design-context file, and accepted choices are recorded as decisions. The explore skill requires three named directions that differ on at least two structural axes, with colour-only variants not counting ([explore skill](https://21st.dev/.well-known/skills/21st-ui-explore/SKILL.md)). The review skill separates deterministic defects from subjective recommendations and forbids silent redesign ([review skill](https://21st.dev/.well-known/skills/21st-ui-review/SKILL.md)). Its component metadata is one sentence naming anatomy, states and variants, up to five tags and a type, with variants modelled as named demos such as `agent-chat/error` and `agent-chat/empty-centered` ([agent-chat.md](https://21st.dev/@serafimcloud/components/agent-chat.md); [openapi.json](https://21st.dev/openapi.json)). It is notable that the marketplace sells spectacle while its own agent guidance sells restraint and project fit.

### Guide additions: a short "standard controls" block and the missing format facts

`CRAFT` is always loaded, so it should carry only the ladder and point to the skill for anatomy. A block of roughly 25 lines in section 3 should state the following. Controls sit on one height ladder of 24, 28, 32, 36 and 40, with 32 or 36 as the desktop default and 44 or more on a phone, and every control in one row shares a height. Horizontal padding is 8 at 24 to 28, 10 to 12 at 32 to 36 and 16 at 40 and above; labels are 14 px at weight 500, meta text is 12 px, icons are 16 beside 14 px text and 12 to 14 beside 12 px text, with a 6 to 8 gap. UI type roles are 12/16, 14/20, 16/24, 18/28 and 24/32 with weights 400 and 500 and 600 for figures only; on a phone, input text is 16 px. Radii come from one base value at 0.6, 0.8, 1 and 1.4 times (6, 8, 10, 14 for a base of 10), and an inner corner equals the outer corner minus the gap between them. Lines are 1 px; in a dark theme they are white at 10% for layout and 15% for inputs, never opaque grey, and surfaces get lighter as they rise. Elevation has three levels: a faint shadow or none on controls, a hairline plus a soft shadow on anything that floats, and a scrim rather than a shadow for dialogs; a hairline plus a shadow on a floating surface is one way of setting it apart, not two. The six colour roles grow to the paired set: background, card, popover, primary and on-primary, secondary, muted and muted text, accent for hover, destructive, border, input and ring. Every interactive control has rest, hover, pressed, focus and disabled, plus its own states, and states are drawn as named frames beside the component. A popup sits 4 from its trigger (8 for popovers), aligns to the trigger's start edge, is at least as wide as the trigger and stays 10 from the frame edge. Numbers that change or sit in a column use one-width figures, right-aligned, with grouped thousands and fixed decimals.

Two existing sentences need rewording. "Set a surface apart in one way only: a line, or a shadow, or a tint" (`craft.rs:95-96`) should carve out floating surfaces. The anti-pattern "Inter/Roboto/Arial by default" (`craft.rs` section 4) should say explicitly that a named library's own face is not a default.

`GUIDE` in `app/src/agent.rs` omits properties the model supports and that component work needs: `layoutPosition: "absolute"` (overlays, badges on avatars, focus-ring backings, close buttons), `textAlignVertical` (single-line labels in fixed-height controls), `underline` and `strikethrough` (links, removed prices), ellipse `innerRadius`, `startAngle` and `sweepAngle` (spinners, progress rings, radio dots), `slot` and the `context` field. Documenting them is a P0 edit. The guide should also list the icon names components rely on structurally (check, chevron-down, chevron-right, chevron-up, x, ellipsis, search, loader-circle or the Lucide name the bundled set uses, panel-left, circle-check, info, triangle-alert, octagon-x), since a wrong name currently draws a placeholder with no advice.

### New skills to write, and what each should contain

All skills should follow the shape the `liquid-glass` skill proved (a decision-oriented `SKILL.md` under 500 lines, `references/` files read on demand, ready-to-insert JSON with stable ids, a final checklist and a symptom, cause, fix table) and borrow the authoring pattern of the emilkowalski skills: a description written as a trigger specification with "use when" and "do not use for" boundaries, numbered hard rules, every value in a table with its reason, and a required closing report. Values should live in one tokens file per skill and be referenced, not repeated.

Two process additions make skills trustworthy. Extend the existing skill test so that every fenced JSON example in every skill is run through the counted review and must produce no mistakes (today's second test validates only material and glass-group fields, `app/src/skills.rs:260-293`). And reuse the fresh-agent harness from `docs/liquid-glass/tests/` with component scenarios (a shadcn-style settings dialog, a button state sheet, a command palette with typed and empty states, a dark dashboard, a phone sheet), then add at least one component sheet to `checks/design-review/`, which today has none.

### New and changed review checks, with proposed thresholds

| Priority | Check | Proposed rule |
|---|---|---|
| P0 | Unknown icon name | Any `icon` layer whose name does not resolve: a mistake in `advice`, naming the nearest valid name. |
| P0 | Outline plus shadow (revise) | Do not count a stroke of 1 px or less whose alpha is 20% or lower; keep the note for opaque outline plus shadow on two or more cards. |
| P0 | Radius count (revise) | Raise the limit from 4 to 5 when every radius is bound to a variable; add a concentric check: a child within 12 of its parent's edge whose radius exceeds parent radius minus the gap by more than 1.5 (the slack `check_glass` already uses). |
| P0 | Default family (revise) | Silent when the request named a library or standard components, or when the document's own variables set the family. |
| P1 | Unequal control heights in a row | Two controls that share a horizontal layout parent and differ in height by 1 to 8: a mistake. |
| P1 | Control ladder | More than 3 distinct control heights in one top-level frame, or a control height that is not a multiple of 4 (pills of 27 or 26 allowed only when a skill is in use): a note. |
| P1 | Side padding of a control | Label with less than 8 left and right (6 when the control is 24 high or less): a mistake, alongside the existing 4 above and below. |
| P1 | Icon discipline | More than 3 distinct icon sizes among 6 or more icons; an icon in a control larger than 1.5 times its label size; icon-to-label gap outside 4 to 8: notes. |
| P1 | Target size | In a top-level frame 480 wide or less, a control under 44 high: a note; anywhere, a control or icon button under 24: a mistake. |
| P1 | Shadow vocabulary | More than 4 distinct shadow recipes in a design of 6 or more boxed frames: a note. |
| P1 | Heavy lines | A uniform stroke of 2 or more on 3 or more boxed frames that are not marked as a focus state: a note. |
| P1 | Dark-theme edges and elevation | On a ground with lightness under 0.25: an opaque stroke lighter than 0.35 on 3 or more frames (suggest white at 10 to 15%); a card or popover whose fill is not lighter than the ground: notes. |
| P1 | Both themes | When the document has a Mode axis, resolve variables in each theme and run contrast in both, whether or not a frame in that theme is on the canvas. |
| P1 | Figure columns | In a column of 3 or more right-aligned figure texts: mixed decimal places or mixed grouping: a mistake. A figure of 5 or more digits without grouping, and "1" followed by a plural noun: notes. |
| P2 | Off-token values | When the document defines radius or spacing variables, more than 3 raw radii or more than 4 raw spacings that match no variable: a note. Count spacing variety (`MOST_SPACINGS`) only over raw values. |
| P2 | Main actions | More than 2 controls carrying the primary fill at the top level of one frame, outside repeated rows: a note. |
| P2 | Effects budget | More than one large blurred light or full-bleed pattern per top-level frame; more than one gradient stroke per frame: notes, silent when the request asked for them. |
| P2 | State coverage (critic, not counted) | When the request or a skill called for states, the critic confirms that frames named for each requested state exist and differ visibly. |

One check should deliberately not be added. WCAG's 3:1 non-text contrast applied to control borders would fail every library here: shadcn's `#e5e5e5` border on white is about 1.3:1 and its focus ring at 50% is not much stronger (my calculations from approximate hex). The defensible rule is narrower: checked and selected indicators and the focus ring must reach 3:1, which Radix's 2 px solid ring does and shadcn's does not. Pencraft's 6:1 rule for text under 13 px should stay; where a library's 12 px muted label fails it, the skill should specify a darker ink for 12 px text and say that this is a deliberate departure.

### Document-model and engine gaps

| Priority | Gap | Why it matters | Interim recipe |
|---|---|---|---|
| P1 | Shadow `spread` is not read | Rings (`0 0 0 Npx`) are how shadcn, Radix, Beautiful UI and Sonner draw focus, hairlines and avatar cut-outs; Tailwind `md` and `lg` shadows and under-glows need negative spread | Hairline as a 1 px alpha stroke; focus as an absolutely placed backing rectangle 2 to 3 larger on each side with radius increased by the same amount; elevation from zero-spread layered stacks. When spread lands, exempt zero-offset, zero-blur shadows from the glow and block-shadow checks. |
| P1 | No OpenType features, so no tabular numerals | Every library that shows numbers turns them on | Keep the per-family figure advice (`craft.rs:249`); add a text property such as `fontFeatures: ["tnum"]` or `numeric: "tabular"`, and have the review prefer it over the family warning. |
| P1 | No variants or states | The model has nothing that prompts more than the resting state | Convention first: the state board and frame naming. Then verify that a `ref` can carry a `theme` override and use a theme axis, for example `State: [Rest, Hover, Pressed, Focus, Disabled]` and `Density`, with per-theme variable values, as the glass skill does with its `Glass` axis. A real `variants` map on reusable components (axis values to descendant overrides) is the eventual fix. |
| P2 | A colour variable cannot take an alpha at the use site | shadcn's recipes are full of `primary` at 80%, `destructive` at 10%, `muted` at 50%, `ring` at 50% | Define explicit tokens (`primary-hover`, `destructive-tint`, `muted-half`, `ring-soft`, `line` and `line-input` as alpha colours) in the skill's `set_variables` call; later allow `"$primary/80"`. |
| P2 | No truncation, max lines, min or max size, or wrapping layout | Names, item descriptions clamped to two lines, chips fields and responsive grids cannot be expressed | Draw truncation by hand with a real ellipsis character and fixed widths; never truncate numbers. Add `maxLines` and truncate first, wrap later. |
| P2 | Several strokes on one layer are not possible | Border plus ring, or inner highlight plus outline, need extra layers | Inner highlight as an inner shadow (y 1, blur 0, white 14%); ring as a backing layer. |
| P3 | No dashed strokes | Empty-state and drop-zone outlines | Solid 1 px line in a quieter colour. |
| P3 | No masks or blend modes | Pattern vignettes, edge fades, screen-blended light | Gradient overlays in the page colour. |
| P3 | Hex only | Sources are OKLCH; conversions drift | Accept `oklch()` on input and store hex, or ship a verified conversion table with the skill. |
| P3 | No corner smoothing | Pills and large radii in Luma-style looks | None needed for standard kits. |

## Conclusion

The libraries turn out to be less a set of competing styles than one shared grammar expressed with different constants: a height ladder, a derived radius scale, paired colour roles, alpha hairlines, role-based elevation and an explicit state list. That reframes Pencraft's problem. Its assistant does not need more taste for component work; it needs a preset, a table and permission to be conventional. The same reframing explains why the first fixes are subtractive: stop dealing a face and a ground to someone who asked for a settings dialog, stop scoring originality on a button sheet, stop flagging a hairline with a shadow. Fidelity to the request is currently enforced only by sentences, while the pull toward distinctiveness is enforced by mechanisms; the plan above gives fidelity mechanisms of its own (a request ledger, a critic class, declared conventions passed to the review).

Two cautions shape the order of work. The component numbers are perishable: shadcn/ui rewrote its default look within twelve months, so every stored value should carry its source and date, and the named-look deltas should live in one reference file that can be re-read from source rather than in `CRAFT`. And none of this has been tested against real output; the gap list comes from reading Pencraft's texts, not from watching a model fail. The cheapest way to find out which additions matter is to write the `ui-components` skill first, run the five fresh-agent component scenarios through the existing harness, and let their friction reports decide which review checks and engine changes come next.
